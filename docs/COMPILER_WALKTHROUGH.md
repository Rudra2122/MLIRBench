# What IREE does to one `linalg.matmul`

This walkthrough follows a single 128×128×128 fp32 `linalg.matmul` through IREE's llvm-cpu pipeline, for two builds:

- **packed** (`packed_mmt4d`): global-opt data tiling, x86 host ISA.
- **direct** (`vec_heuristic`, `vec_autotuned`): no data tiling, the matmul is tiled and vectorized in place.

Every snippet below is copied from files generated by `python -m mlirbench ir`. They live in `results/ir/<variant>_128x128x128/`, one file per phase (`01_input.mlir` … `09_hal.mlir`), plus `llvm/*.ll` and `llvm/*.s`. The summary of each phase is in `summary.json`.

For each step: what changed, why the compiler did it, what it means for memory and layout, and what it means for the hardware.

---

## 0. Source (`00_source.mlir`)

```mlir
%filled = linalg.fill ins(%cst : f32) outs(%init : tensor<128x128xf32>) -> tensor<128x128xf32>
%r = linalg.matmul ins(%A, %B : tensor<128x128xf32>, tensor<128x128xf32>) outs(%filled ...)
```

This is value-semantic tensors with no loops, memory, or target yet. The whole program is one named op.

## 1. Global optimization: data tiling (`02_global-optimization.mlir`, packed build)

```mlir
%pack   = linalg.pack %A outer_dims_perm = [0, 1] inner_dims_pos = [0, 1] inner_tiles = [16, 1]
            : tensor<128x128xf32> -> tensor<8x128x16x1xf32>
%pack_0 = linalg.pack %B outer_dims_perm = [1, 0] inner_dims_pos = [1, 0] inner_tiles = [16, 1]
            : tensor<128x128xf32> -> tensor<8x128x16x1xf32>
%7      = linalg.mmt4d ins(%pack, %pack_0) outs(%6 : tensor<8x8x16x16xf32>)
%unpack = linalg.unpack %7 ... inner_tiles = [16, 16] -> tensor<128x128xf32>
```

- **What changed.** The one matmul became four ops: pack A, pack B, `mmt4d` (a matmul on 4-D tile-major operands with a transposed RHS), and unpack C.
- **Why.** The inner tile sizes (M0, N0, K0) = (16, 16, 1) are chosen from the *target*: 16 fp32 lanes = one 512-bit zmm register on this AVX-512 host. The v1 build targeted a generic CPU, and its flow IR shows `inner_tiles = [8, 1]` / `[4, 1]` and `mmt4d_16x32x128x8x4x1`, sized for 128-bit SSE. Same source, different layout, purely because of the target flag.
- **Memory and layout consequence.**
  - Packed A stores, for each 16-row block, all K values with the 16 rows contiguous. Packed B does the same for 16 columns, so B's columns become contiguous (the transpose is `outer_dims_perm = [1, 0]`).
  - The inner kernel can then stream both operands with unit stride.
  - The cost: every call now reads A and B, writes packed copies, then reads those. `05_stream.mlir` shows the copies explicitly as a transient allocation, 3 × 64 KiB for packed A, B and C:
    ```mlir
    stream.resource.alloca uninitialized ... : !stream.resource<transient>{%c196608}
    ```
- **Hardware consequence.** See step 4. The packing pays off only if the inner kernel's gain exceeds the extra traffic. The ladder measures exactly that:
  - At 128³ packing loses: 0.0476 ms vs 0.0397 ms direct.
  - At 1024³ it wins by about 2.5×: 21.3 ms vs 54.2 ms direct.
  - For the 1×4096×4096 GEMV it loses badly: packing B copies 64 MB per call for 33 MFLOP of work.

## 2. Dispatch creation → Flow (`03_dispatch-creation.mlir`, `04_flow.mlir`)

```
flow: matmul_dispatch_0_pack_f32, matmul_dispatch_1_pack_f32,
      matmul_dispatch_2_mmt4d_8x8x128x16x16x1_f32, matmul_dispatch_3_unpack_f32
```

- **What changed.** Each op above was outlined into its own `flow.executable`, called through `flow.dispatch`. The direct build has one dispatch, `matmul_dispatch_0_matmul_128x128x128_f32`, with the `linalg.fill` fused into it, so C is zero-initialised in registers rather than written and re-read.
- **Why.** A dispatch is the unit of device work. Fusion decides what shares a dispatch, and so what never round-trips through memory. Here pack and unpack are *not* fused into the mmt4d dispatch, so they are separate passes over memory.
- **Consequence.** Four kernel launches instead of one. At 128³ each launch costs a measurable share of 40–50 µs; the invocation floor for a 1×1×1 matmul is 2.3 µs. The `packed_late` variant (dispatch-creation data tiling) instead materializes the layout late as encoding dispatches. At 128³ it is the slowest data-tiled option (68 µs), and at 512³ and above the fastest (2.44 ms at 512³).

## 3. Stream → HAL (`05_stream.mlir`, `09_hal.mlir`)

- **Stream** makes resources and ordering explicit. The four dispatches are recorded inside one `stream.cmd.execute`, with `ro` / `wo` access ranges on the transient buffer. This is where the packed copies become real allocations.
- **HAL** turns that into `hal.command_buffer.dispatch` ×4 plus a workgroup count per export. From `08_executable-targets.mlir`:
  ```
  pack A  -> hal.return %c16, %c1, %c1    (16 workgroups)
  pack B  -> hal.return %c256, %c1, %c1   (256 workgroups)
  mmt4d   -> hal.return %c1,  %c1, %c1    (1 workgroup)
  unpack  -> hal.return %c16, %c1, %c1
  ```
- **Consequence worth noticing.** At 128³ the compute dispatch has **one** workgroup: the distribution tile `[8, 8]` covers the whole 8×8 outer tile grid. On the single-threaded `local-sync` device this doesn't matter. On `local-task` with N threads, the mmt4d cannot be parallelised at this size, while the cheap pack of B is split 256 ways. This is a concrete, checkable prediction for a multi-core follow-up.

## 4. Codegen configuration (`07_executable-configurations.mlir`)

This phase is where tile sizes are decided. This is what the autotuner overrides.

Packed build, mmt4d dispatch:
```mlir
translation_info = #iree_codegen.translation_info<pipeline = Mmt4dTilingExpert>
linalg.mmt4d {lowering_config = #iree_cpu.lowering_config<distribution = [8, 8, 0, 0, 0, 0],
   vector_common_parallel = [1, 1, 0, 16, 16, 0], vector_reduction = [0, 0, 1, 0, 0, 1]>}
```
The register tile is one 16×16 inner tile, i.e. 16 zmm accumulators.

The pack of B is configured `vector_common_parallel = [1, 1]`. It is a transposing pack and is not vectorized, unlike pack A (`[1, 16]`).

Direct build, IREE heuristic:
```mlir
linalg.matmul {lowering_config = #iree_cpu.lowering_config<distribution = [16, 64, 0],
   vector_common_parallel = [8, 16, 0], vector_reduction = [0, 0, 16]>}
```
Direct build, autotuned (MLIRBench-selected, passed in through `#iree_codegen.compilation_info`):
```mlir
linalg.matmul {lowering_config = #iree_cpu.lowering_config<distribution = [16, 64, 0],
   vector_common_parallel = [4, 64, 0], vector_reduction = [0, 0, 16]>}
```

- **Why the heuristic loses at 128³.** Its register tile is 8×16: 8 rows × 1 zmm = **8 accumulator registers**. On this class of Xeon core an AVX-512 FMA has ~4-cycle latency with 2 FMA ports (the measured 171 GFLOP/s peak is consistent with 2 ports × 16 lanes × 2 FLOP at ~2.7 GHz), so at least 8 independent accumulators are needed just to cover latency, with no slack for loads.
  - The tuned tile 4×64 is 4 rows × 4 zmm = **16 accumulators**, the same count the packed mmt4d kernel uses.
  - Result: 0.0308 ms vs 0.0397 ms (1.29× in the confirmation run).
- **Upper limit.** Going past the 32 architectural zmm registers spills. In `results/autotune/128x128x128.json`, 16×64 tiles (64 accumulators) show 154–382 vector stack accesses in the dispatch function, against 0 for non-spilling tiles (the `.s`-wide count, 176–404, also includes 22 from runtime helpers the linker drops; see [ELF_AND_DWARF.md](ELF_AND_DWARF.md)), and throughput collapses to 68–73 GFLOP/s. The static spill count and the timing agree.

## 5. LLVM IR and assembly (`llvm/*.ll`, `llvm/*.s`)

The `vector.contract` from the register tile becomes `llvm.intr.fmuladd` on `vector<16xf32>`. From the phase summaries:

- 128 `fmuladd` calls in the heuristic build.
- 64 in the tuned build.
- 16 in the mmt4d kernel.

The x86 assembly shows two different inner-loop shapes.

Direct, autotuned: register-register FMAs, with B rows loaded as full vectors and A elements broadcast into registers:
```asm
vfmadd231ps  %zmm19, %zmm20, %zmm13
vfmadd231ps  %zmm18, %zmm20, %zmm12
```
Packed mmt4d: the A element is **broadcast straight from memory** as part of the FMA (`{1to16}`). That works only because packing made the 16 A values for a K step contiguous:
```asm
vfmadd231ps  -60(%rax,%r10){1to16}, %zmm16, %zmm0
vfmadd231ps  -56(%rax,%r10){1to16}, %zmm16, %zmm1
```
This is the layout consequence of step 1 showing up as an instruction choice.

**v1 build, for contrast.** With `--iree-llvmcpu-target-cpu=generic`, IREE 3.11 lowers the mmt4d tile to the portable `iree_uk_mmt4d_tile_f32f32f32_generic` microkernel. Its assembly contains **zero packed FMAs**: scalar `mulss` / `addss` / `movss`, 128-bit registers at most. That is the whole 30–50× gap in the ladder, and it comes from one missing flag, not from memory bandwidth.

## 6. RISC-V: the same dispatch, different backend

With `+v` the dispatch lowers to RVV:

- `results/riscv.json` shows 9 vector FMAs (`vfmacc`/`vfmadd`) and a `vsetvli`.
- The `rv64gc` build has 0 vector FMAs and 269 scalar `fmadd.s` instead.

Both are linked as static libraries into `harness/static_dispatch_harness.c` and executed under `qemu-riscv64`:

- They pass at VLEN 128, 256 and 512.
- The RVV build traps with SIGILL when V is disabled, which proves the vector code is on the executed path.

This validates correctness and ISA selection. It is not a RISC-V performance result.

## 7. What the hardware counters say about these transformations

The sections above tie each transformation to its assembly. Hardware counters on an Intel Emerald Rapids host (GCE C4, [`COUNTER_FINDINGS.md`](COUNTER_FINDINGS.md)) tie them to what the CPU actually did.

| Walkthrough claim | Measured |
|---|---|
| Step 5: the v1 generic build is scalar | 100% scalar FP instructions retired; 1.42 of 64 FLOP/cycle; L1 miss rate 0.23%, so the limit is instructions, not memory |
| Steps 4–5: the direct build is AVX-512 FMAs | 100% of retired FP instructions are 512-bit packed; FLOP count exactly 2·M·N·K |
| Step 4: 16 accumulators beat the heuristic's 8 | Autotuned 512³ sustains 59.1 of 64 FLOP/cycle vs 37.7 for the heuristic; L2 traffic at 1.04× the compulsory minimum vs 2.16× |
| Step 1: packing's layout pays off at large sizes | At 1024³ packed moves as much data through L2 as tuned direct code (25× vs 23× compulsory) but stalls on L2 misses in 4% of cycles vs 22%, and holds ~40 FLOP/cycle from 512³ to 1024³ |
| Step 1: packing costs extra traffic at small sizes | At 512³ packed fills L2 with 3.2× the compulsory bytes vs 1.04× for tuned direct code, and loses (1.76 vs 1.28 ms) |

## 8. Writing the codegen yourself

Everything above describes what IREE's pipeline does. [`TRANSFORM_SCHEDULE.md`](TRANSFORM_SCHEDULE.md) replaces that pipeline for the matmul with a hand-written transform-dialect schedule ([`schedules/matmul.mlir.in`](../schedules/matmul.mlir.in)). It performs the steps of sections 4–5 explicitly:

- cache tile → workgroups;
- register tile → `vector.contract`;
- contraction → outer-product FMAs;
- accumulator hoisting.

It reaches parity with IREE's pipeline at 128³ and 512³. It then adds a K-blocking step that IREE's configuration cannot express, which matches or beats IREE's best option at 1024³: a tie on GCE C4, 1.16× faster on the sandbox VM. Counters confirm the effect (2.5× fewer L2 misses, one-third the L2 stall cycles); the cause on C4 is not fully established.
